# 《灯影山海》Dev 实验计划

> 状态：实验准备已获用户授权，实验结论尚未获批  
> 授权日期：2026-10-01  
> 实验范围：阴影、幕布、判定频率、整局复位  
> 硬边界：全部实验资产只能位于 `Content/DengYingShanHai/Dev/`，不得被正式地图引用

## 1. 实验原则

> *永远不要以牺牲架构设计为代价追求功能；永远不要基于猜测进行权衡——必须与我确认。*

1. 每次实验只改变一个主要变量，其他相机、灯位、皮影姿态、分辨率和画质设置保持一致。
2. 每个候选必须保存配置、截图/录屏、性能数据、异常记录和复现步骤。
3. “画面更好看”“感觉更流畅”不能单独作为结论，必须说明观察条件和可比较证据。
4. 实验结束只输出推荐，不自动修改正式关卡、正式 Data Asset 或 Shipping 配置。
5. 所有推荐都必须写入 `Docs/ARCHITECTURE_DECISIONS.md`，等待用户确认后才能将状态改为 `Accepted`。
6. 测试不得引入付费资产、未审查插件或引擎源码修改。
7. 如果实验需要改变核心接口、状态机或依赖方向，立即停止，先向用户说明影响并请求确认。

## 3. 公共测试基线

阴影和幕布实验使用同一套测试基线：

- 固定 Cine Camera Transform、焦距、曝光设置和输出分辨率；
- 固定灯的 Transform、强度、色温、衰减范围和阴影设置；
- 固定皮影 Transform、姿态和动画时间点；
- 固定幕布尺寸、场景背景和后处理；
- 使用同一台目标演示电脑和同一套画质配置；
- 先完成着色器预热，再开始采样；
- 每个候选至少记录静止、灯移动、皮影移动、姿态切换四种情况；
- 不用不同镜头掩盖候选方案的缺陷。

基础测试资产优先使用 UE 基础几何和项目自制测试纹理，确保结论不依赖第三方美术资源。

## 4. EX-SHADOW-01：视觉 Mesh 与 Shadow Caster

### 4.1 目的

确定夸父视觉皮影能否独立产生稳定、准确的实时阴影；只有在它无法满足演出需求时，才考虑增加同骨架 Shadow Caster。

### 4.2 候选

| 候选 | 视觉 Mesh | Shadow Caster | 说明 |
|---|---|---|---|
| A | 可见并投影 | 无 | 最小结构，首选基线 |
| B | 可见但关闭投影 | 同骨架、仅投影 | 验证分离后能否提升稳定性 |

不增加第三套预烘焙或贴图假影方案，以免偏离“真实 UE 阴影”的核心要求。

### 4.3 控制变量

- A、B 使用同一骨架、同一动画、同一世界 Transform；
- Shadow Caster 不允许通过人工位移修饰单个截图；
- 两套方案使用同一灯光和幕布候选；
- 关闭与实验无关的额外动态投影灯；
- 对齐检查覆盖静态姿态和运动全过程。

### 4.4 证据

- 正面、侧面和幕后视角截图；
- 灯与皮影连续运动录屏；
- 阴影轮廓是否抖动、断裂、穿插或偏移的记录；
- 视觉 Mesh 与 Shadow Caster 骨架姿态差异记录；
- `stat unit`、`stat gpu` 或 Unreal Insights 中的可比较数据；
- Actor/组件配置截图；
- Development 包中的重复验证结果。

### 4.5 淘汰条件

- Shadow Caster 与视觉 Mesh 无法在完整动画中保持一致；
- 玩家能直接看到重复几何或错误的投影体；
- 方案需要破坏 `ADYPuppetActor` 的统一骨架边界；
- 只在编辑器中有效，打包版本不一致；
- 为修复单个镜头引入大量逐镜头特例。

### 4.6 输出

输出 A/B 对比，不直接修改 ADR-004。推荐必须说明画面稳定性、实现复杂度、性能成本和回退方式，然后交由用户确认。

## 5. EX-SCREEN-01：幕布承影结构

### 5.1 目的

在保持真实阴影可读的前提下，让幕布具有纤维、透光和幕后空间层次，同时避免透明排序和高 Overdraw 破坏稳定性。

### 5.2 候选

| 候选 | 结构 | 目的 |
|---|---|---|
| A | 单层 Opaque/Masked 承影幕 | 建立最稳定、最低复杂度基线 |
| B | Opaque/Masked 承影层 + 薄 Translucent 视觉叠层 | 分离承影与纤维透光表现 |
| C | 单层 Translucent 幕布 | 作为对照，验证动态阴影、排序和可读性风险 |

候选 C 不是默认路线，保留它是为了让排除结论有实测证据。

### 5.3 材质参数范围

只开放以下实验参数：

- Base Color / Tint；
- Roughness；
- Opacity 或 Mask Threshold；
- Normal/Fiber 强度；
- 幕布前后光照贡献；
- 必要的轻微边缘暗化或污渍层。

不在该实验中引入复杂 Substrate 网络、自定义 HLSL 或第三方材质插件。

### 5.4 证据

- 玩家正面视角、幕后视角和斜角截图；
- 静态与运动阴影录屏；
- 透明排序、噪点、闪烁、边缘断裂和背景泄露记录；
- Shader Complexity / Quad Overdraw 对比；
- GPU 时间和材质指令信息；
- 在统一曝光下的阴影对比度；
- Development 包与编辑器一致性。

### 5.5 淘汰条件

- 阴影在正常演出距离下无法快速辨认；
- 玩家移动或镜头切换时出现明显排序错误；
- 必须依赖逐镜头材质切换才能维持画面；
- 候选结构使幕后与幕上空间关系变得不可读；
- 打包版本与编辑器效果不一致且无法稳定复现。

### 5.6 输出

输出三候选对比和推荐层级，不直接修改 ADR-005。若推荐双层幕布，必须同时说明组件间距、防止 Z-fighting 的方法、阴影落在哪一层以及调试可见性规则。

## 6. EX-EVAL-01：判定采样频率

### 6.1 目的

确定通用 Evaluator 的采样频率，使正确趋势、进入区间和持续确认反馈足够及时，同时不让判定依赖每帧 Tick。

### 6.2 候选

- 10 Hz；
- 15 Hz；
- 20 Hz。

这些是实验采样点，不是最终认可数值。Evaluator 的核心函数保持纯逻辑、与调用频率解耦。

### 6.3 测试输入

使用相同的可重复参数轨迹：

1. 缓慢接近目标；
2. 快速穿过目标；
3. 在进入容差附近往复；
4. 进入后短暂离开；
5. 正确姿态与错误姿态切换；
6. 输入样本暂时无效；
7. 达成后继续输入，验证成功只触发一次。

优先通过自动化测试或预定义轨迹驱动，而不是三次手动操作后凭感觉决定。

### 6.4 记录指标

- 从进入目标区间到反馈变化的延迟；
- 从持续条件满足到成功事件的延迟；
- 快速穿越是否误判成功；
- 边界反馈切换次数；
- 宽限和迟滞行为是否与定义一致；
- Evaluator 调用耗时；
- Game Thread 对比；
- 玩家盲测中是否能感知迟滞或不响应。

### 6.5 淘汰条件

- 相同输入轨迹产生非确定结果；
- 采样频率改变后持续确认的实际时间明显失真；
- 快速穿越目标会错误完成谜题；
- 必须把视觉阴影作为补充判定才能稳定工作；
- 为某一幕加入专用 Tick 逻辑。

### 6.6 输出

输出 10/15/20 Hz 的数据和盲测记录，不直接修改 ADR-006。推荐值以及是否需要对调试模式使用不同频率，必须再次由用户确认。

### 6.7 已确认结论（2026-10-02）

- 10/15/20 Hz 的频率独立性自动化测试均通过；Holding 由真实世界时间累计，不按样本数计算；
- 用户完成 M1 人工 PIE 检查并确认键鼠操作正常；
- 用户明确确认采用 15 Hz，ADR-006 已在 `ARCHITECTURE_DECISIONS.md` 转为 Accepted；
- Development 屏幕调试仍独立限频为最高 4 Hz，Shipping 不显示；
- 本结论只固定逻辑采样基线，不固化 P01/P02 的 Target、Tolerance 或正式视觉反馈参数。

## 7. EX-RESET-01：整局复位方式

### 7.1 目的

比较“重新加载关卡”和“原地重建运行时状态”两种整局复位方式，选择在比赛现场最可靠的路线。

### 7.2 候选

| 候选 | 方式 | 主要观察点 |
|---|---|---|
| A | 重新加载当前关卡 | 引用重建可靠性、黑屏/加载时间、资源缓存 |
| B | Director 驱动原地复位 | 复位速度、状态残留、委托重复、Sequencer 清理 |

无论最终选择哪一种，“当前谜题复位”仍必须通过 Director 的状态和快照协议完成，不由 Level Blueprint 临时拼接。

### 7.3 复位检查清单

- Experience State 回到起始状态；
- Current Puzzle 和完成标志清零；
- 灯和皮影回到定义快照；
- 持续确认、宽限和成功边沿清零；
- Sequencer、音频和 Niagara 停止且回到基线；
- Presentation Token 失效，旧回调被忽略；
- 动态委托没有重复绑定；
- UI 和字幕恢复；
- 第三幕“成林”资产完全清理；
- 再次完整通关不受前一次运行影响。

### 7.4 测试序列

分别在以下节点触发复位：

1. 开场中；
2. 第一幕未进入目标时；
3. 持续确认中；
4. 幕间过渡中；
5. 第三幕成功边沿；
6. 成林演出进行中；
7. 完整结束后。

每个候选执行重复循环，记录第一次与后续循环是否出现差异。正式循环次数在读取现有测试设施和目标电脑情况后确定，不基于猜测写死。

### 7.5 证据

- 各节点复位录屏；
- 复位耗时；
- 内存与对象数量前后对比；
- 重复委托、过期 Token 和残留 Actor 日志；
- 多轮完整通关结果；
- Development 与 Shipping 包的对比；
- 崩溃、软锁和无法再次交互的复现记录。

### 7.6 淘汰条件

- 出现一次可复现的流程软锁或崩溃；
- 复位后存在残留成功状态或重复事件；
- 旧 Sequencer 回调可以推进新一轮流程；
- 只在编辑器有效；
- 需要 Level Blueprint 保存额外核心状态。

### 7.7 输出

输出可靠性、耗时、复杂度和回退成本，不直接修改 ADR-009。最终方案由用户确认。

## 9. 实验完成后的决策流程

```text
完成实验
→ 保存证据
→ 写实验报告
→ 更新 ADR 为“有证据、待确认”
→ 向用户展示候选差异和推荐
→ 用户确认
→ ADR 改为 Accepted
→ 才允许迁移或重建到正式目录
```

不允许直接把 `Dev/` 资产拖入正式地图作为“暂时方案”。正式采用时应在正确目录创建或迁移经确认的最终资产，并检查重定向器、引用和 Cook 范围。

## 10. 开始实施前的只读检查

建立任何 C++ 文件或 `.uasset` 前必须确认：

- 实际 `.uproject` 文件名与 `EngineAssociation`；
- 实际游戏模块名和 `Build.cs`；
- 已存在的 `Source/` 类与命名；
- Content Browser 中是否已经存在同名目录或资产；
- 当前默认地图、GameMode 和输入配置；
- 已启用插件；
- 当前工作区未提交修改，避免覆盖队友内容；
- UE 编辑器是否可通过目标引擎打开；
- Development 编译与基础打包是否仍可通过。

只读检查无法完成时，不猜测模块名、不生成 `.uasset`、不创建可能冲突的 C++ 类。
